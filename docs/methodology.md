# Методика расчёта Apollon

Расчёт детерминирован и выполняется чистыми функциями TypeScript. Ни API модели, ни база данных не участвуют в математике. Срез данных задаётся датой: обучение включает только законченные месяцы, а текущий незаконченный месяц не экстраполируется в обучающую выборку. Отрицательные продажи остаются в исходной истории и обнуляются только для обучения.

## Разовые продажи

Строки объединяются по товару и счёту с сохранением возвратов. Счёт не является идентификатором клиента. Для автоматического распознавания счёта нужны минимум шесть ранее датированных положительных счетов. Порог равен максимуму `median + 6 × MAD × 1.4826`, `Q3 + 3 × IQR` и трёх типичных сезонных месячных объёмов. Счёт должен составлять не менее 30% месяца. Если минимум три из следующих шести доступных на дату среза месяцев также повышены, увеличение считается устойчивым.

Вычитание из месячного отчёта разрешено только при расхождении подписанного итога счетов с месячным отчётом не более 5%. При отсутствии сверки используется отдельный месячный фильтр на сезонно скорректированном ряду; он заменяет выброс типичным сезонным объёмом. Для рядов, у которых более 40% месяцев нулевые, оба автоматических фильтра отключены. Менеджер может восстановить любую коррекцию по стабильному идентификатору. Если действительно есть обезличенный `customerId`, проверяется сумма одного клиента за скользящие 60 дней; на реальных книгах эта ветка не доказывается, поскольку идентификаторы клиентов отсутствуют.

## Доступность и упущенный спрос

Пустой остаток трактуется как ноль только строго между первым и последним известным остатком товара. За пределами этого периода значение неизвестно. Подтверждённые интервалы дефицита имеют приоритет; пересечения дней учитываются один раз. Иначе при продажах ниже 80% сезонной нормы и нулевом начальном или следующем остатке доступность оценивается по последнему дню продажи либо отношению наблюдаемых продаж к ожидаемым.

`Упущенный спрос = ожидаемый сезонный спрос × (1 − доступность)`. Прибавка ограничена так, чтобы восстановленный объём не превысил две нормы; существующие большие продажи не уменьшаются. Для оценки выводится чувствительность при изменении доступности на ±0,25 — это сценарный диапазон, не статистический доверительный интервал. Для подтверждённых интервалов диапазон совпадает с точечной оценкой. Компенсацию можно отключить либо задать доступность товара/месяца вручную.

## Сезонность, рост и прогноз

Сезонный профиль товара строится из отношений к среднему объёму года, при минимум девяти наблюдаемых месяцах года, с ограничением влияния экстремальных объёмов. При объединении профилей каждый товар сначала нормируется; объединение происходит только внутри одинаковых единиц измерения. Индексы имеют среднее 1. Собственный профиль сжимается к групповому с весом `полные годы / (полные годы + 1)`. Денежные коэффициенты поставщика не используются для прогноза количеств.

Уровень и Theil–Sen тренд оцениваются на последних 12 сезонно скорректированных месяцах; оценённый годовой тренд ограничен ±50%. Уровень приведён к последнему законченному месяцу. Пользовательский или предоставленный поставщиком коэффициент роста заменяет оценённый рост; режим сложения задаётся явно. Единственная точка отсчёта роста — последний законченный месяц. Прогноз месяца равен `уровень × сезонность × (1 + годовой рост)^(месяцы от точки отсчёта / 12)`. Месячный объём делится на календарные дни.

## Запас и заказ

Горизонт `H = срок поставки + период пересмотра`, оба в днях. Ошибки одношагового прогноза рассчитываются последовательно: каждое наблюдение прогнозируется только по предшествующей истории. При минимум 12 ошибках страховой запас равен положительному эмпирическому квантилю уровня сервиса, умноженному на `√(H/30)`. При меньшей выборке применяется `z × σ_месяц × √(H/30)`. Это приближение предполагает независимые месячные ошибки. Нижняя граница страхового запаса — спрос за настроенное число дней. Категория изменяет уровень сервиса и минимальные дни запаса; значения являются предположениями, категории не получают выдуманных значений.

Свободный остаток уже учитывает резерв; резерв повторно не вычитается. Начальный остаток можно превратить в оценку текущего через подписанные продажи и подтверждённые полученные поставки. Прошедшая ETA не означает получение: неподтверждённые просроченные поставки не добавляются к остатку и требуют проверки. Известный текущий снимок используется с его датой; при устаревшей дате показано предупреждение. Неизвестный остаток условно равен нулю с обязательной проверкой. Отрицательный остаток не скрывается.

Дневная проекция добавляет будущие поставки только в день ETA. Чистая потребность равна `max(0, спрос_H + страховой запас − свободный остаток − будущие поступления внутри H)`. Большая поздняя поставка может обнулить заказ, но ранний дефицит остаётся виден и сохраняет критическую срочность. При положительной потребности применяется MOQ, затем округление вверх до отдельной кратности упаковки. Если задан коэффициент перевода закупочной единицы в единицу спроса, MOQ и кратность сначала умножаются на него; количество заказа и его единица остаются в единицах спроса.

ABC рассчитывается по восстановленному спросу за последние 12 месяцев отдельно по единицам; для Systeme Electric с известной стоимостью используется стоимость потребления. Товары без стоимости образуют отдельные группы по единицам. Границы A/B/C — 80%/95% накопленного вклада. XYZ основан на коэффициенте вариации: X ≤0,5, Y ≤1, иначе Z; это аналитическая характеристика, не бизнес-категория.

## Историческая проверка

Используются срезы 31 мая, 30 июня и 31 июля 2026, горизонты 1–3 месяца с доступными полными фактическими месяцами по август включительно. На каждом срезе заново строятся профили, фильтры и прогноз. Будущие продажи, остатки, счета и дни дефицита удаляются. Неверсионированный текущий коэффициент роста исключается. Сравниваются модель, тот же месяц прошлого года и среднее 12 месяцев. Метрики: MAE, WAPE и средняя подписанная ошибка. При нулевой сумме фактического спроса WAPE не определён (`null`). Смешивать метры и штуки для бизнес-интерпретации общей ошибки нельзя. Наблюдаемые продажи могут недооценивать спрос из-за отсутствия товара; это ограничение оценки.

Проверки запускаются из диалога **«Проверка расчёта»** на единственной странице `/` (вкладка «Проверки кейса»), либо напрямую через `GET /api/checks`; оба пути вызывают один и тот же движок — пять прозрачных синтетических сценариев. Они подписаны как синтетические; экспорт утверждённой версии и ревизионная блокировка проверяются на уровне приложения. Все допущения, пороги, промежуточные значения и предупреждения сохраняются в обосновании каждой рекомендации.

## Точные константы из `lib/engine`

Приведённые ниже значения — не иллюстрация, а буквальные константы кода на дату этого чекпоинта (`lib/engine/index.ts`, `ENGINE_THRESHOLDS`; `lib/contracts/engine.ts`, `DEFAULT_POLICY`). Любое изменение констант в коде должно сопровождаться обновлением этой таблицы.

| Константа | Значение | Где используется |
|---|---|---|
| `reconciliationTolerance` | 0.05 (5%) | Допуск сверки счетов и месячного отчёта |
| `minimumPriorInvoices` | 6 | Минимум предыдущих счетов для автоматического исключения разового заказа |
| `invoiceMonthlyShare` | 0.3 (30%) | Минимальная доля счёта в месячном объёме для флага |
| `monthlyRatio` | 3 | Множитель типичного сезонного объёма в пороге разового заказа |
| `madMultiplier` | 6 | Множитель `MAD × 1.4826` в пороге |
| `iqrMultiplier` | 3 | Множитель IQR в пороге (`Q3 + 3×IQR`) |
| `persistenceMonths` | 6 | Окно проверки устойчивости роста после подозрительного месяца |
| `persistenceMinimum` | 3 | Минимум повышенных месяцев из `persistenceMonths`, чтобы не считать выброс разовым |
| `intermittentZeroShare` | 0.4 (40%) | Доля нулевых месяцев, при которой оба автоматических фильтра выключаются |
| `annualTrendCap` | 0.5 (±50%) | Предел годового тренда Theil–Sen |
| `availabilitySensitivity` | 0.25 (±25 п.п.) | Диапазон чувствительности оценки доступности |

Значения политики по умолчанию (`DEFAULT_POLICY`, редактируются в разделе «Расширенные настройки» на единственной странице `/` перед расчётом):

| Параметр | Значение по умолчанию |
|---|---|
| `leadTimeDays` | 45 дней |
| `reviewDays` | 30 дней |
| `serviceLevel` | 0.95 (95%) |
| `safetyDays` | 7 дней (нижняя граница страхового запаса) |
| `growthMode` | `replace` (предоставленный/сценарный рост заменяет оценённый тренд) |
| `categoryServiceLevels` | категория 1 → 0.98, 2 → 0.95, 3 → 0.92, 5 → 0.90, 7 → 0.85 |
| `categorySafetyDays` | не заданы по умолчанию; наследуют `safetyDays` |
| `stockoutCompensation`, `outlierFiltering` | включены (`true`) по умолчанию |

Категории 1/2/3/5/7 — это единственные значения категории, встреченные в исходных данных Systeme Electric (см. §12 `BUILD_PLAN.md`); их бизнес-смысл партнёром не раскрыт, поэтому уровни сервиса по категориям — явные редактируемые допущения, а не проверенная политика.
